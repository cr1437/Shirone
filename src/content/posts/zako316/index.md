`zako3.16` 处理的是一件比 bug 更麻烦的事：**有人在冒充我**。

事情的起因是社区里有人提醒我，外面流传着一些 "Shizako+" 之类的改名重打包版本，署名乱七八糟。顺着这条线索查下去，最让我后背发凉的发现不是外面那些人干了什么，而是——**我自己的 GitHub 版 APK，解包之后长得很像一份仿冒品**。

这一版就是冲着「彻底解决」去的。除此之外，看门狗那个「重试三次就永久放弃」的老毛病也一起修了。

## 0. 这一版改了什么

| 类别 | 内容 |
| --- | --- |
| 治理 | GitHub 版停发上游身份占位包（占用上游包名 `moe.shizuku.privileged.api`、应用名 "Shizuku" 的空壳子包） |
| 新增 | 应用内签名自检：启动时比对签名证书指纹，不符弹警告引导核对（只警告、不阻断） |
| 新增 | 「设置 → 关于」展示当前安装包自己的完整签名指纹与校验状态，点按复制 |
| 加固 | 看门狗断线重连改为三级策略：3 秒快重试 ×3 → 每 5 分钟低频恢复，直到成功 |
| 加固 | 冷恢复：开机后 binder 从未上报时，主动探测并按上次激活方式拉起服务 |
| 修复 | 开着保活点「停止服务」，3 秒后服务又被看门狗拉起来 |
| 修复 | 常驻通知如实显示「低频重试中」与「已按主人要求停止」，不再假装在岗 |

前三条是防伪，后三条是稳定性。正文按这个顺序讲。

## 1. 外面的仿冒，和我自己的问题

先说外部环境。GitHub 上 Shizuku 的 README 里明确写了：**禁止 fork 使用 "Shizuku" 名称**（Apache-2.0 §6 附加条款）。我的项目从一开始就守规矩：包名用自己的 `com.churan.shizako`，权限名用自己的，provider authority 用自己的，从没碰过上游的包名和应用名。

但社区提醒之后我去搜了一圈，确实有人在把各种改名重打包的版本丢到第三方站点上，署名 "SILENT KILLER" 之类的都有。这些站点上的东西我没法管——用户装了什么，只有用户自己能校验。**我能做的，是让「校验」这件事在用户侧变得极其简单**：一枚抄不走的签名指纹。

而真正让我坐不住的是另一半发现：**我自己的 GitHub 版 APK 里，内嵌了一个 `assets/shizako-stub.apk`**。解包它，`aapt2 dump badging` 的输出是这样的：

```
package: name='moe.shizuku.privileged.api'
application-label: 'Shizuku'
```

一个占着**上游包名**、应用名叫**"Shizuku"** 的空壳子包，躺在我自己的发布产物里。这个东西的历史使命，是讨好那些把老包名写死的第三方客户端——但它逐字违反上游 Apache-2.0 §6 的附加条款。更要命的是**观感**：任何人解包我的官方 APK 跑一次 `aapt2 dump badging`，都会看到一个叫 "Shizuku"、包名是 `moe.shizuku.privileged.api` 的子包。从外部看，这和一份「下载了 Shizuko、重打包改名」的仿冒品**无法区分**。

我在打自己的脸。F-Droid 版早就把它关掉了（不 include `:stub` 模块 + 构建时删 APK），GitHub 版却一直带着。这就是本版第一条改动的由来。

## 2. 停发占位包：连根拔

这不是删一个文件的事，得把整条链拔掉：

- **`settings.gradle`**：原来在 `-Pfdroid` 条件下 include `:stub` 模块。现在任何变体都不再构建 stub，模块本身（`stub/` 目录）整个删掉；
- **`manager/build.gradle`**：`COMPAT_STUB_PACKAGE` 这个 BuildConfig 字段恒为空串；`compatAuthority` 只保留自有 authority `com.churan.shizako.shizuku`；`copyStubApk` / `removeStubApk` 两个构建任务及挂在它们上面的 `preBuild` 依赖一并删除；
- **运行时**：`StubManager.kt`（三条安装通道的汇总逻辑）删除，实验室页面里的 stub 状态展示、`strings_lab.xml` 里全部 `lab_stub_*` 字符串删除；
- **starter 侧**：`ServiceStarter.java` 里有一处兜底——manager 包名为空时回退到 `"moe.shizuku.privileged.api"`。占位包都没了，这个回退就是颗地雷，删。

删完之后我做了核验：新 APK 里没有任何内嵌 APK，所有 provider authority 都是 `com.churan.shizako.*`，`aapt2 dump badging` 里再也找不到 `moe.shizuku` 的包名、权限和 label。

**文档同步**：README、README_EN、NOTICE、编译文档里所有「兼容桥 / provider authority / 不能共存」的旧描述全部改写，并新增「官方构建的签名指纹」一节。

## 3. 应用内签名自检：抄不走的那个维度

占位包拔了，第二个问题浮出来：**用户怎么知道手里这份 APK 是不是我发的？**

仿冒品可以抄我的界面、抄我的包名、甚至抄我的版本号——但有一样东西抄不走：**发布证书的私钥**。签名指纹是仿冒者唯一的硬性障碍，因为重新打包必然重新签名，指纹必然不同。而在这之前，这枚指纹只躺在我的笔记里，用户侧**没有任何手段**校验。

所以有了 `security/SignatureGuard.kt`，逻辑非常直白：

1. 启动时读**当前这个安装包自己**的签名证书，算 SHA-256；
2. 和官方发布指纹 `515BAF0C…9F9C8A` 比对（README 里公示的同一枚，从正式发布的 APK 用 `apksigner verify --print-certs` 实测读出）；
3. 不符 → 弹警告：展示你这份的指纹、一键打开官方发布页核对、一键复制自己的指纹去比对。

几个 deliberate 的设计决定：

- **只警告、不阻断**。这是我的明确选择：误报（比如用户自己用调试证书签名编译）不该让软件变砖。警告+引导核对，把判断权还给用户；
- **F-Droid 版不弹**。F-Droid 用自己的密钥重签是必然现象，指纹必然和官方不同且应用内无法预知——对它弹警告等于狼来了。F-Droid 版在关于页标注「F-Droid 签名」即可；
- **每进程只弹一次**。弹一次够说明问题了，不需要 recreate 一次弹一回。

「设置 → 关于」页新增签名指纹卡：状态徽标（官方签名 / F-Droid 签名 / 无法确认）+ 等宽字体分段显示的完整 64 位指纹，点按复制。用户拿着复制出来的串和 README 一对，三秒钟的事。

说句实话：这套防线的威慑力不在于拦住多少伪造安装包——真要比拼的是渠道和用户习惯。它的意义在于**把「校验官方性」的成本降到接近零**，让每一个装了我软件的人都能自己确认：我装的就是开发者发的那一个。

## 4. 看门狗：从「重试三次就放弃」到三级重连

说完防伪说稳定性。这条线的起因是复查保活逻辑时看到的两个洞。

**洞一：失败三次，永久放弃。** 看门狗原来是这样处理服务崩溃的：binder 死亡 → 3 秒后快重试，最多 3 次 → 超过就什么都不做，干等 binder 自己回来。可是 binder 凭什么自己回来？无线调试关了、adbd 重启了、服务进程僵死了——这些场景下它**永远不会自己回来**。用户看到的就是：通知显示「已崩溃 3 次，将重试…」，然后永远转圈。所谓重试，一次都不会再发生。

**洞二：开机后没人去拉服务。** 手机重启后，看门狗自己会被闹钟或 shell 小看门拉起来——但这时候 binder **从未上报过**，死亡回调根本不会触发。老逻辑里「等 binder 死了再救」的整套机制，在冷启动场景下完全失效。服务就静静地躺在那里，没人管。

现在的三级策略：

1. **快重试**：binder 死亡 → 3 秒后拉起，连试 3 次（保留原行为）；
2. **低频恢复**：3 次都失败 → 转入恢复模式，每 5 分钟探测并拉起一次，**直到成功才退出**。频率选 5 分钟是耗电与响应速度的折中——看门狗的每一轮都要 fork 进程、读 `/proc`，不能像快重试那么密；

   > **补记（zako3.16hp）**：这一段发布时是准确的，但很快就发现它有个洞——**如果压根没有可用的拉起方式**（上次是无线调试激活、5555 不通、又没拿到自动开无线调试的权限），恢复循环会什么都不做却每 5 分钟醒一次，而通知还在说「正在重试」。所谓「直到成功」，前提是「有路可走」。这一点已在 `zako3.16hp` 修掉，详见文末补记。
3. **冷恢复**：看门狗自己被拉起时，如果探测到服务没在跑、且以前成功激活过（mode 已记录）、且主人没有刚手动停过——5 秒后按上次的激活方式（root / adb）主动拉起。补的就是开机这个洞。

顺带修掉一个更基础的 bug：**开着保活时点「停止服务」，3 秒后服务又被看门狗拉起来了**。原因很朴素——`Shizuku.exit()` 触发 binder 死亡回调，看门狗把它当崩溃处理，安排重启。主人的明确操作被自己的保活逻辑推翻，这是逻辑自相矛盾。现在四个停止入口（首页状态卡、首页对话框、快捷磁贴、Tasker）都会先调 `WatchdogService.noteIntentionalStop()`：既放过紧随的死亡回调，也把自动重连压制 30 分钟。30 分钟后如果主人还是没管，保活继续——这符合「看门狗」这个词的语义。

通知栏也终于会说人话了：新增「低频重试第 N 次」和「已按主人要求保持停止」两个状态，不再无论实际情况都显示「已崩溃，将重试…」。

## 5. 构建与验证

- GitHub 版、F-Droid 版双变体 `assembleRelease` 均通过；
- APK 内核验：三语文案（英/简中/繁中）齐全、官方指纹常量在 DEX 里、权限表与包名标签无上游残留；
- 版本号 `versionCode 316` / `zako3.16`，更新日志、开发文档（`docs/dev/changelog.html` 由 `tools/md2html.py` 生成）同步。

## 6. 想说的

这个项目从「重打包改名的 Fork」起家（合规的那一种），现在花一整版的时间把自己洗成**从任何角度都验明正身**的样子——身份、签名、指纹公示、自检——某种意义上是个轮回。

对装了这个软件的人，我只说一句：**校验指纹只要三秒**。设置 → 关于，点一下复制，和 GitHub README 里那行 `515BAF0C…` 对一下。对不上，你手里的就不是我发的。这个动作值得成为习惯——不只对我，对你装的每一个关键软件都值得。

服务保活这边，还是那句话：她存在的意义是**你不用管她**。死线了会救，开机会自己回来，你让她停她就老老实实停着。

以上。zako3.16 见。

## 补记：zako3.16hp

文章发出去之后我回头把配对与激活这条链路从头审了一遍，翻出两个问题，其中一个正是上面第 4 节的自打脸——**我说「直到成功才退出」，但没说清楚「如果根本无路可走会怎样」**。

- **低频恢复会空转**：上次是无线调试激活、5555 不通、又没有自动开启无线调试的权限时，恢复逻辑什么都不做，却依然每 5 分钟醒一次，永远等不到成功，而通知一直显示「正在重试」。现在它会停表，并如实说「自动重连已放弃——请手动启动服务（或重新授权限 / 改用 Root）」，另加了约 1 小时的尝试上限。**这版修的是「通知别再宣称一件做不到的事」**，和第 3 节签名自检是同一个毛病：界面不该替事实说话。
- **配对每次尝试都漏资源**：配对客户端是可关闭的，但两条调用路径都从来不关它。于是每次配对尝试——**包括每次失败后的重试**——都会漏掉两个文件描述符和一块原生内存，而那里面存着 SPAKE2 密钥的拷贝。失败重试恰恰是配对设计上预期的高频操作。

`zako3.16hp` 已发布：[github.com/cr1437/Shizako/releases/tag/zako3.16hp](https://github.com/cr1437/Shizako/releases/tag/zako3.16hp)。
`versionCode` 仍是 316，只有 `versionName` 加了 `hp` 后缀，可以直接覆盖安装 zako3.16；签名指纹不变，仍是 `515BAF0C…9F9C8A`。

有一件事值得单独写下来，因为它是这一版最值钱的部分：**上面那两个问题，我自己第一轮审查时看得太浅，是后来「再检查看看」才挖出来的**。而复查里最关键的一次不是读代码，是把改动真的编译了一遍——`WatchdogService` 加日志时漏了一个 `import`，纯读代码完全看不出来。更早一轮我还差点被 Gradle 的 `FROM-CACHE` 骗过去，以为「clean 过了」就算验过了。

所以第 6 节那句「校验指纹只要三秒」，我想再加半句：**看代码也值得再看一遍。**
